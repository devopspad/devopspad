# 01 场景与需求

## 要管理的对象

按“OPC 运营一个产品矩阵实际要操心的东西”盘点，而不是按技术分类。

| 对象 | 例子 | 现在在哪 | 要回答的问题 |
| --- | --- | --- | --- |
| 产品 | heartie、thumbsnap、某个工具站 | 脑子里 | 有哪些产品，各在什么阶段，用了哪些资源 |
| 服务 | heartie-admin、heartie-api、定时任务、静态站 | 各代码仓库 | 代码在哪、跑在哪、怎么构建、怎么发版 |
| 环境 | dev / pro | `project.yaml`（局部） | 每个环境对应哪个集群 / 命名空间 / 机器 |
| 机器 | 香港 2C4G、家里的 NAS | 云控制台 + `workspace.json` 连接 | IP、SSH 方式、角色、跑了哪些服务、多少钱、何时到期 |
| 集群 | 一台机器上的 K3s | `workspace.json` 连接 | 由哪些机器组成，kubeconfig 从哪取 |
| 域名 | heartie.app 及子域 | 注册商 + DNS 服务商 | 注册商、DNS 在哪、何时到期、解析指向哪、证书怎么签 |
| 数据存储 | MySQL、Redis、对象存储桶 | `workspace.json` 连接 + 云控制台 | 谁在用、在哪、怎么备份 |
| 镜像仓库 | 自建 registry、GHCR | 记忆 | 地址、凭据在哪 |
| 第三方账号 | 云厂商、Cloudflare、Stripe、App Store、邮件、统计、AI API | 密码管理器 + 记忆 | 哪些产品用了这个账号，套餐、费用、续费日、凭据存在哪 |
| 配置文件 | Nginx conf、ConfigMap、`.env` 模板、systemd unit | 服务器上手改 / 集群里 | 当前内容是什么，谁在什么时候改过，和期望是否一致 |
| 操作记录 | 发版、改配置、重启、手工处理 | `releases/`、`runs/`（局部） | 发生过什么，谁做的（人还是 AI），结果如何 |
| 运维笔记 | 排障步骤、踩坑、上线清单 | 聊天记录 / 笔记软件 | 遇到同样的问题怎么处理 |

## 用户故事

每条都写了验收方式，A1 阶段（见 [05](05-roadmap.md)）至少完成标了 ★ 的。

### 全貌

- ★ **矩阵总览**：我能在一个页面 / 一条命令看到所有产品、状态、域名、所用机器和每月费用。
  验收：`devopspadcli report matrix` 输出表格；桌面“档案”首页显示同样内容。
- ★ **反查依赖**：我想下线一台机器，能看到它上面跑了哪些服务、属于哪些产品，哪些域名解析到它。
  验收：`devopspadcli refs host:hk-1` 列出所有引用方。
- **成本**：按产品汇总每月费用，共享资源按比例分摊。
  验收：`devopspadcli report cost` 输出产品维度和账号维度两张表。

### 防事故

- ★ **到期提醒**：域名、证书、机器、订阅在 30 天内到期的都能列出来。
  验收：`devopspadcli report renewals --within 30`；桌面首页提醒。
- **配置留档**：线上 Nginx / ConfigMap 被改过时，档案库能看到差异，并能把线上版本存档。
  验收：`devopspadcli config diff` / `config pull`（A3）。
- ★ **操作留痕**：每次发版、改配置、手工处理都有记录，能看出是人还是 AI 做的。
  验收：现有发版记录继续可用；手工操作可通过 `devopspadcli note` 补记（A1）。

### 换设备 / 恢复

- ★ **新电脑恢复**：克隆档案库，补齐本机密钥后，DevOpsPad 里的连接全部恢复。
  验收：`devopspadcli secrets check` 列出缺失的密钥；`devopspadcli connect sync` 从档案生成本机连接（A2，A1 先做 check）。

### 产品生命周期

- **新产品上线清单**：新建产品时生成清单（域名、DNS、证书、机器 / 集群、镜像仓库、CI、监控、备份），逐项勾选。（A1 由 Skill 的 onboard 流程覆盖，命令以后再做。）
- **产品下线清单**：关停时列出该产品独占的资源（域名、订阅、机器、数据库），避免继续扣费；共享资源只解除引用。
  验收：A1 由 Skill 的 sunset 流程用 `refs` 逐项生成清单；专门的清单命令以后再做。

### AI

- ★ **AI 查上下文**：在任意产品仓库里让 Claude Code “把 heartie-admin 发到生产”，它能通过 Skill 找到环境、集群、发版方式和注意事项。
- ★ **AI 维护档案**：让 AI “把新买的域名 foo.app 登记一下，DNS 在 Cloudflare，指向 hk-1”，它能按协议写出 YAML，校验通过后提交。
- **AI 排障**：AI 先读档案库了解拓扑，再用只读工具查日志和事件（依赖 [../04 M2](../04-roadmap-draft.md)）。

## 规模假设

实际规模（2026-11-07 确认）：**上百个产品，2 台机器**。产品多、机器少：几乎所有产品共用两台机器和同一个集群，管理重点在产品、域名、账号和到期，而不是机群。

| 项 | 设计上限 |
| --- | --- |
| 产品 | 300 |
| 服务 | 1,000 |
| 机器 | 10 |
| 域名 | 500 |
| 第三方账号 | 100 |
| 操作记录 | 每年 1 万条 |

在这个规模下，所有档案文件每次全量读进内存校验，不需要数据库和索引服务。实测：500 个产品（约 2,000 个资源、7,000 条引用）完整校验约 0.4 秒；`internal/archive/scale_test.go` 用 300 个产品防止性能退化。

产品多带来的要求：`report matrix -l <标签> --stage <阶段>` 筛选；用 `metadata.labels`（如 `line=tools`）给产品分组；Skill 支持批量登记（一次登记几十个产品、一次提交）。
