# OPC 矩阵档案库（Archive）规划

日期：2026-11-07
状态：A0 + A1 已实现（2026-11-07），使用说明见 [docs/archive.md](../../archive.md)；决策见 [06](06-open-questions.md)

## 背景

一人公司（OPC）同时运营多个产品，形成产品矩阵。每个产品都有自己的域名、机器、集群、服务、配置、第三方账号和订阅费用，而且很多资源在产品之间共用（一台机器跑三个产品，一个 Cloudflare 账号管十几个域名）。

现在这些信息散落在各云控制台、服务器手改的文件、各代码仓库、记忆和聊天记录里。问题是：

- 不知道全貌：哪台机器跑了什么、一个产品用了哪些资源、每月花多少钱。
- 容易出事故：域名、证书、订阅到期没续；手改配置没有记录，出问题无法回溯。
- 换设备难：换电脑或重装后，连接、配置要重新找一遍。
- AI 缺上下文：让 AI 改代码、发版、排障时，它不知道这个产品部署在哪、配置在哪、怎么发版。

## 目标

> 用一个 **Git 管理的档案库** 记录整个产品矩阵的全部资产和配置；DevOpsPad（桌面 + `devopspadcli`）负责读写、校验、采集和执行；AI 通过 **Skill + CLI（以后加 MCP）** 按同一协议安全地查询和维护档案。

三个关键词：

1. **协议**：档案库有固定的目录布局、资源格式（`apiVersion` / `kind` / `metadata` / `spec`）、引用语法、密钥引用规则和记录格式，有 JSON Schema，可被程序严格校验。
2. **留档**：期望状态（人/AI 维护）和操作记录（引擎生成）进 Git，可回溯；观测快照（采集生成）只留在本机，不进 Git。
3. **AI 可用**：给 AI 一份 Skill，告诉它档案库的模型、规则和标准流程；所有读写都通过 `devopspadcli`，写入后必须校验。

## 不做什么

- 不存任何密钥明文。档案库只存密钥**引用**（OS 钥匙串 / 环境变量 / 本机文件路径），不接密码管理器。
- 不是 CMDB 平台，不需要服务端。档案库就是一个私有 Git 仓库，Git 托管随意（GitHub 私有库、自建 Gitea、SSH bare 仓库）。
- 不替代代码仓库。服务代码、Dockerfile、CI 配置仍在各自仓库，档案库只记录“在哪里、怎么连、怎么发”。
- 第一阶段不对线上做写操作。写线上仍走现有的发版引擎，以后统一到 Action 引擎（见 [../06](../06-ai-devops-control-plane.md)）。

## 一句话结论

档案库就是 [../05 Q3](../05-open-questions.md) 一直没定下来的“统一领域模型”的落地形式。建议：

1. 先定协议和 Schema（A0），再做**只读 + 文件级**的档案库能力和 Skill（A1）。这一步不碰线上，风险低，但马上能解决“全貌、续费、换设备、AI 上下文”四个痛点。
2. 再做采集和漂移（A2）、配置文件归档（A3）。
3. 最后让档案库成为 Action 引擎的输入，现有 `project.yaml` / `fleet.json` / `releases/` / `runs/` 并入档案库（A4，对应 M1）。
