# 03 产品定位

## 已确定的方向（2026-11-06）

> **AI 驱动的本地优先 DevOps 控制面**：控制 CI、群控机器和 K3s 集群，让 AI 在人设定的策略和审批范围内完成构建、发版、运维和排障，所有动作都有计划和记录。

对应原来的三个选项：

| 原选项 | 现在的位置 |
| --- | --- |
| B 小团队运维发版工作台 | **基础**：机器、集群、发版、配置、记录 |
| C AI 执行控制面 | **主线**：AI 通过 MCP / CLI 调用同一个 Action 引擎 |
| A Navicat 式数据库客户端 | **配套**：保持只读，作为排障时 AI 和人的数据查询工具 |

架构草案见 [06-ai-devops-control-plane.md](06-ai-devops-control-plane.md)。

## 差异化

1. **零服务端**：桌面 + CLI + SSH，目标机器不装 Agent，不需要部署平台。
2. **AI 原生**：能力以 MCP 工具暴露，AI 拿不到凭据，写操作必须经过计划、策略和审批。
3. **可信记录**：记录由执行引擎生成，而不是 AI 自报；可通过 Git 在小团队中共享。
4. **全链路**：同一个工具覆盖 CI、K3s、宿主机 Nginx / 服务和中间件查询。

## 竞品参照

| 类别 | 代表 | Infradex 的区别 |
| --- | --- | --- |
| K8s 平台 | Rancher、Kuboard、Lens | 不只管 K8s，还管宿主机和 CI；AI 是一等用户 |
| GitOps | Argo CD、Flux | 不需要集群内控制器；适合几台 K3s 的小规模场景 |
| 配置管理 | Ansible、Salt | 有 UI 和计划 / 审批；动作是结构化的，不是任意 playbook |
| AI 运维 | 各类 K8s MCP Server | 带策略、审批、机群编排和统一记录，不只是包装 kubectl |

## 主要风险

- **AI 误操作的后果是真实的**：策略和审批必须先于 AI 写能力上线（见 04 的顺序）。
- **范围膨胀**：CI、机群、K8s、数据库全都想要。必须按里程碑收窄，每期只打通一条链路。
- **零服务端的限制**：定时任务、webhook、远程审批都需要常驻进程。先接受这些限制，等确实需要再做 `infradexd`。
